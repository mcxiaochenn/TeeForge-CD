## 1. P1：RKP `TA 响应长度无效`

### 1.1 当前调用链

```text
rkp/mod.rs:107  worker::sign(&tmp, &request)
  └─ worker.rs:70   ta::request(&request)            # 子进程
       └─ ta.rs:88  (send)(object, req, len, resp, 0xa000)
       └─ ta.rs:104 response_payload(&response)      # ① 剥帧 → 返回 payload
  └─ worker.rs:73   json!({"ok":true,"payload": base64(payload)})
  └─ worker.rs:59   parse_reply(&reply)              # ② base64 解码，原样返回 payload
rkp/mod.rs:108  protocol::response_payload(&response) # ③ 再剥一次帧 —— 错
```

`response_payload` 的契约是「输入带 8 字节帧头的原始缓冲区，输出 payload」。**③ 的入参已经是 payload**，却被当成缓冲区再解一次。

### 1.2 两个独立缺陷

**B1 —— 双重解帧（确定性错误，100% 复现）**

`rkp/mod.rs:108`：

```rust
let csr = protocol::unwrap_csr(&protocol::response_payload(&response)?)?;
```

`response` 是 CBOR 字节流，被当作 `[i32 status][u32 len]` 解析：

- 前 4 字节被读成 `status`；
- 第 4..8 字节被读成 `length`；
- 只要 `length` 为 0 或越过 `BUFFER_SIZE - 8`，就抛 `frame/payload_length`。

这不是"某些固件才有的差异"，而是**只要 ① 成功，③ 就必然在错误数据上做判断**。哪怕 ① 侥幸通过，③ 也会产出一段被砍掉头部的假 CSR，后续 `validate_csr` 仍会失败。

**B2 —— 帧布局假设过窄（本次报错的真实来源）**

`protocol.rs:365-404` 只认一种布局：

```text
[ i32 status (LE) ][ u32 payload_len (LE) ][ payload … ]
```

`payload_len == 0` 或超界即报错。若该固件的 `send_cmd` 返回的是其他布局（无 status、长度含头、纯 payload、大端等），第一次解析就会失败。

`ta.rs:104` 的错误经 `worker.rs:74` 被 `error.to_string()` 字符串化，父进程 `parse_reply` 再用 `TfError::new` 重建——**`stage` / `code` / `hint` / `raw` 全部丢失**。这解释了为什么 WebUI 只显示一句中文，看不到 `status`、`length`、`head_hex`（这些字段 `protocol.rs:395-401` 其实已经采集了）。

### 1.3 一个积极信号

`payload_length` 这个分支要求 `response.len() >= 8` 且 `status == 0`。能走到这里说明：

1. 厂商库加载、符号解析、构造/析构都成功；
2. `send_cmd` 返回 0（TA 未拒绝）；
3. 缓冲区被写过（不是哨兵 `0x80000000`）。

也就是说**厂商调用链已经打通，问题只在我们怎么读它返回的字节**。这与社区在小米 17 Pro 上的成功案例一致。不要因为这次的报错就否定设备路径。

### 1.4 修复方案

**Step 1：拆职责，让帧解析只有一处**

把 `ta::request` 的返回值改为**原始缓冲区 + 调用状态**，不再在 TA 层剥帧：

```rust
pub(crate) struct RawFrame {
    pub(crate) bytes: Vec<u8>,   // 完整 0xa000 缓冲区
    pub(crate) status: i32,      // send_cmd 返回值
}
```

`worker.rs` 回执改为：

```json
{
  "ok": true,
  "frame_b64": "…",
  "frame_len": 40960,
  "written": 1234,          // 与哨兵比对后估算的有效区间上界
  "head_hex": "0000000…"
}
```

父进程拿到 `RawFrame`，由 `rkp/mod.rs` 唯一一次解析。这样「谁负责剥帧」不再有歧义，也不可能再出现双重解析。

**Step 2：业务驱动的自适应解帧**

新增 `protocol::decode_frame`，按候选布局依次切片，**用业务解析函数判定是否命中**，而不是只检查长度字段是否"看起来合理"：

```rust
pub(crate) enum Layout { StatusLen, StatusTotal, LenOnly, StatusOnly, Bare }

pub(crate) fn decode_frame<T>(
    buf: &[u8],
    accept: impl Fn(&[u8]) -> Result<T>,
) -> Result<(Layout, T)>
```

候选与判据：

| 顺序 | 布局 | 切片 | 说明 |
|---|---|---|---|
| 1 | `StatusLen` | `buf[8..8+len]`，要求 `status == 0`、`0 < len <= 0xa000-8` | 现有假设，优先保持兼容 |
| 2 | `StatusTotal` | `buf[8..total]`，`total` 含 8 字节头 | 长度语义是"总长"的固件 |
| 3 | `LenOnly` | `buf[4..4+len]` | status 由返回值给出，不在缓冲区 |
| 4 | `StatusOnly` | `buf[4..]`，尾部连续 0 截断 | 无长度字段 |
| 5 | `Bare` | `buf`，尾部连续 0 截断 | 纯 payload |

`accept` 传入业务解析器：

- CSR：`unwrap_csr`（已校验 `AuthenticatedRequest` 结构）
- EEK 链：`[ [[curve, [certs…]], …], challenge ]` 结构校验
- 证书链：`[ [shared, [unique…]] ]` 结构校验

命中后把 `Layout` 记入 `meta.json` 与日志；未命中则返回 `frame/exhausted`，`raw` 里带前 64 字节 hex、缓冲区实际写入区间、`send_cmd` 状态。

这样做的关键理由：**长度字段可以骗人，能解出合法业务结构才是真的**。同时顺序固定、可测试，不会出现"随机选一个能跑就行"的不确定性。

**Step 3：结构化错误跨进程**

`worker.rs` 回执从 `{"ok":false,"error":"字符串"}` 改为：

```json
{ "ok": false, "error": { "stage": "frame", "code": "payload_length",
                          "message": "…", "hint": "rkp.frame.payload_length",
                          "raw": { … } } }
```

`TfError` 增加 `from_parts(stage, code, message, hint, raw)` 用于还原。父进程保留 fallback：若回执仍是旧的字符串格式（升级瞬间的子进程），按 `TfError::new` 处理。

**Step 4：文案补齐**

当前 i18n 缺 `rkp.ta.status` 与 `rkp.frame.*`，前端 `RkpPage.vue:51-56` 又只查 `rkp.code.<code>`，所以即使补 hint 也不会显示。统一为：

```ts
const explain = computed(() => {
  const hint = issueError.value?.hint;
  if (hint && hasKey(hint)) return t(hint);
  const code = issueError.value?.code;
  const key = code ? `rkp.code.${code}` : '';
  return key && hasKey(key) ? t(key) : '';
});
```

三个语言各补：`rkp.frame.payload_length`、`rkp.frame.truncated_header`、`rkp.frame.exhausted`、`rkp.frame.abi`、`rkp.ta.status`。

### 1.6 验证

主机侧（可自动化）：

- 五种布局的构造夹具各跑一次，断言命中的 `Layout` 正确；
- 全零缓冲区 → `frame/exhausted`，`raw.head_hex` 为 64 个 0；
- 业务解析失败时继续尝试下一布局，不提前返回；
- worker 回执新旧两种格式都能解析；
- 回归：`mod.rs` 不再出现第二次 `response_payload`（可用一个「payload 已是 CBOR」的夹具断言不报 `payload_length`）。

真机（小米 17 Pro）：

```sh
su -c '/data/adb/modules/teeforge_cd/teeforge --rkp-issue --json' | tee /sdcard/rkp.json
```

**分层探测：用当前已装版本就能做，不必等新版**

`json::fail` 只输出存在的字段。若错误来自子进程，`worker.rs` 的 `to_string()` 会让 `stage/code/hint/raw` 全部丢失，信封里只剩 `message`；若错误来自父进程 `rkp/mod.rs:108` 的第二次解析，则会带上 `stage`、`code`、`raw.head_hex`。

```sh
su -c '/data/adb/modules/teeforge_cd/teeforge --rkp-issue --json > /sdcard/rkp.json 2>/sdcard/rkp.log'
```

| 信封特征 | 含义 | 对计划的影响 |
|---|---|---|
| 有 `stage:"frame"`、`code:"payload_length"`、`raw.head_hex` | 第一次解析已成功，错误出在第二次 | **B1 是唯一根因**，B2 不必启用；修完即通 |
| 只有 `message`，无 `stage` / `raw` | 第一次解析就失败（`ta.rs:104`） | B2 存在，必须要新版把 `head_hex` 透出 |

这一步零成本，且能把 S4 的往返次数减少一半。

判定顺序：

1. 成功 → `RKP/keybox.xml` 生成，`meta.json.frame_layout` 记录命中的布局；接着 `--keybox --source rkp` 安装。
2. 仍失败 → 看 `raw.head_hex` 与 `written`，按下表分诊：

| 现象 | 结论 | 下一步 |
|---|---|---|
| 前 8 字节全 0，`written` 很小 | TA 返回空成功 | 检查请求帧与 `security_level`，考虑先调 `get_version` 握手 |
| 首字节是 `82`/`a2`/`d2` 等 CBOR major type | 纯 payload | `Bare` 应已命中，若未命中说明 `accept` 过严 |
| `[00 00 00 00][非零长度][CBOR]` | 无 status | `LenOnly` |
| `[非零 status][len][…]` | 长度语义不同 | `StatusTotal` 或大端 |
| 前 4 字节仍是 `00 00 00 80` | 缓冲区未被写 | 参数顺序或 out 缓冲区无效，需复核 ABI |

这张表直接对应 `decode_frame` 的候选顺序，失败信息本身就是下一步的输入。

### 1.7 风险

- **自适应解析引入误命中**：靠业务结构校验与固定顺序缓解；命中布局写入 `meta.json`，可回溯。
- **`RawFrame` 让 worker 回执变大**：0xa000 base64 ≈ 54 KB，超过当前 `MAX_REPLY_BYTES = 64 KiB` 的余量不多。方案：只回传**有效区间**（`written` 上界向上取整 1 KiB），并让 `MAX_REPLY_BYTES` 提到 128 KiB。这是本轮唯一需要动的超时/上限参数。
- **`send_cmd` 符号名已编码参数类型**（`EPvjS1_j` = `void*, unsigned, void*, unsigned`），因此不需要做 ABI 矩阵探测；若上表最后一行成立，应优先怀疑缓冲区大小或调用前置条件，而不是参数顺序。

## 2. P2：WebUI 视口溢出

### 2.1 根因

**R1 —— 导航栏负外边距撑破容器（左右溢出的确定原因）**

`App.vue`：

```html
<div class="shell safe-x min-h-dvh">
  <AppBar … />
  <main class="mx-auto w-full max-w-[560px] px-4 pb-10">
```

`AppBar.vue:22` 用 `-mx-4 px-4`。但 `AppBar` 是 `.shell` 的**直接子元素**，`.shell` 只有 `safe-x`（通常为 0），**没有 `px-4`**。于是：

- `margin-left/right: -16px` → 块级自动宽度 = 容器宽 + 32px；
- 内容靠 `px-4` 补回视觉对齐，但**盒子本身已经越界 32px**；
- `.shell` / `body` 都没有横向裁剪 → 文档可横向滚动。

`TargetPage.vue:233` 的吸底条也用 `-mx-4`，但它在 `main` 的 `px-4` 内，是正确抵消，**不要动**。

**R2 —— 强制撑满视口（上下溢出的原因）**

```css
/* tailwind.css:19-31 */
body { min-height: 100vh; min-height: 100dvh; }
```

叠加 `App.vue` 的 `.shell { min-h-dvh }`。在 KernelSU 管理器的 WebUI 容器里：

- `100vh` 取的是「最大视口高度」，不等于 iframe 实际高度；
- 沉浸式状态栏下 `dvh` 也会把系统栏区域算进去。

结果页面比可视区高一截，内容不多也能上下拖动。

**R3 —— viewport 未限制缩放**

`index.html:5` 只有 `width=device-width, initial-scale=1.0, viewport-fit=cover`。双指缩放后页面可平移，表现为"不合预期的滑动"。

### 2.2 修复

**布局**（`App.vue` / `AppBar.vue`）：

```html
<!-- App.vue：去掉 min-h-dvh -->
<div class="shell safe-x">

<!-- AppBar.vue：删掉 -mx-4 px-4，内层补 px-4 -->
<header class="sticky top-0 z-30 backdrop-blur-xl backdrop-saturate-150 safe-top" :style="…">
  <div class="mx-auto flex h-14 w-full max-w-[560px] items-center gap-2 px-4">
```

这样导航栏背景宽度等于容器内容宽度，不再越界；`safe-x` 为 0 的设备上视觉与现在完全一致。

**全局样式**（`tailwind.css`）：

```css
html { height: 100%; }

body {
  min-height: 100%;      /* 不再用 vh/dvh */
  overflow-x: clip;      /* 兜底：不创建滚动容器，不影响 sticky */
  overscroll-behavior: none;
}

@supports not (overflow: clip) {
  body { overflow-x: hidden; }
}
```

`overflow-x: clip` 优先，因为 `hidden` 会让 `body` 成为滚动容器，可能让 `position: sticky` 的吸底条失效；`clip` 不创建滚动容器。`@supports` 兜底给旧 WebView。

`.shell` 的 `min-h-dvh` 一并移除，高度交给内容。

**viewport**（`index.html`）：

```html
<meta name="viewport" content="width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no, viewport-fit=cover" />
```

**浮层高度**（`AppSheet.vue`）：`max-h-[86vh]` → `max-h-[86dvh]`，并保留 `max-h-[86vh]` 作为回退行。

### 2.3 验证

自动化（无头浏览器，可脚本化）：

```js
// 每个页面、390 与 360 两个宽度各跑一次
const el = document.documentElement;
report = {
  hOverflow: el.scrollWidth - el.clientWidth,   // 必须 == 0
  vOverflow: el.scrollHeight - el.clientHeight, // 首页必须 == 0
};
```

需覆盖：首页、目标作用域、Keybox、RKP、更新、偏好浮层打开态。任何 `hOverflow > 0` 即失败。

真机（小米 17 Pro）：

- 页面四边贴边，无横向可拖动；
- 首页内容不足一屏时不能上下拖动；
- 双指缩放无效；
- 目标页列表滚动时吸底条保持吸底，导航栏保持吸顶。

## 3. P3：版本号多一个 `v`

### 3.1 根因

三个来源格式不一致：

| 来源 | 实际值 | 说明 |
|---|---|---|
| `module/module.prop` | `version=0.6.0` | 无前缀 |
| CDN `release.json` | `"version": "v0.6.0"` | 带前缀 |
| 前端显示 | 手动拼 `v` | 第三处再补一次 |

具体位置：

- `DeviceHeader.vue:59` → `v{{ props.data.module.version }}` → `v0.6.0`
- `HomePage.vue:69` → `'v' + session.data.module.version` → `v0.6.0`
- `UpdatePage.vue:135` → `{{ info.latest.version }}` → `v0.6.0`（来自 CDN）
- `UpdatePage.vue:96` → `{{ info.current.version }}` → `0.6.0`（来自 module.prop）

结果同一屏里 `0.6.0` 与 `v0.6.0` 并存。

### 3.2 修复

新增 `webroot/src/lib/format.ts`：

```ts
/** 统一版本展示：去掉已有的 v/V 前缀，保证各来源一致。 */
export function formatVersion(raw?: string | null): string {
  if (!raw) return '—';
  return raw.replace(/^[vV]/, '');
}
```

替换四处：

- `DeviceHeader.vue:59`：`{{ formatVersion(props.data.module.version) }}`（去掉硬拼的 `v`）
- `HomePage.vue:69`：`:badge="session.data ? formatVersion(session.data.module.version) : undefined"`
- `UpdatePage.vue:135`、`:209`：`formatVersion(info.latest.version)`
- `UpdatePage.vue:96`：一并走 `formatVersion`，保持同源同格式

**不改** `module.prop` 与 `release.json` —— 前者是模块规范字段，后者被 Magisk/KernelSU 的更新检查直接消费，改动风险大于收益。归一化只发生在展示层。

### 3.3 验证

- 首页徽章、更新页"当前版本"与"可用更新"三处均显示 `0.6.0`；
- CDN 清单无论写 `0.6.0` 还是 `v0.6.0`，显示一致；
- 缺字段时显示 `—`，不出现 `vundefined`。

## 6. 分阶段

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| S0 | 用**当前已装版本**跑一次 `--rkp-issue --json`，只看信封里有沒有 `stage` / `raw` | 能判定错误发生在子进程还是父进程（见 1.6 的分层探测） |
| S1 | P3 版本号归一化 | 三处显示一致，无 `v` |
| S2 | P2 布局修复 | 无头检测 `hOverflow == 0`；真机四边贴边 |
| S3 | P1 拆职责 + 自适应解帧 + 结构化错误 | 主机 5 种布局测试全绿；`cargo test` 无回归 |
| S4 | 真机验收 | `--rkp-issue` 成功或拿到可判读的 `raw.head_hex` |

S1/S2/S3 互不依赖，可并行；S4 是唯一需要设备的环节。

## 7. 待确认

1. **版本号是否统一不带 `v`**。当前计划按"去掉 v"实现（`module.prop` 是 `0.6.0`，模块生态惯例也如此）。若你希望统一显示 `v0.6.0`，只需把 `formatVersion` 改成加前缀，调用点不变。
2. **P1 的自适应解帧是否要保留 `StatusLen` 优先**。保留能保证已经跑通的固件行为不变；若你更希望"以业务解析结果为准、不预设顺序"，可以改成遍历所有布局取第一个业务解析成功者，但会失去可预测性。
3. **真机日志回传方式**。S4 需要你把 `/sdcard/rkp.json` 或 `logs/` 内容发我，否则无法判断 `head_hex` 属于上表哪一行。
